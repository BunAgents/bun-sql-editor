Why your SQL editor can't be a pure PWA (and what we did instead)

Progressive Web Apps are genuinely impressive. Service workers, Web App Manifest, OPFS, IndexedDB, background sync — modern browsers are powerful application runtimes. A lot of software that used to require native apps can now be PWAs.

But not a SQL editor that connects to external databases. Here's why.

What PWAs can do

A PWA can:

  • Install to your home screen or desktop
  • Work offline via service worker caching
  • Store data locally with IndexedDB or OPFS
  • Make HTTP/HTTPS requests to any server
  • Open WebSocket connections
  • Run CPU-intensive code via WebAssembly

This is a rich platform. Many apps — note-taking, drawing tools, code editors, even IDEs — work beautifully as PWAs.

The one thing PWAs can't do

Open a raw TCP connection.

That's it. That's the wall. Browsers are deliberately prevented from opening arbitrary TCP sockets. The Direct Sockets API exists as a proposal for isolated web apps, but it's not available in standard browser contexts and requires special permissions not available to regular websites.

Why does this matter? Because database protocols are TCP:

DatabaseProtocolBrowser accessible?
PostgreSQLCustom binary over TCP:5432✗ No
MySQLCustom binary over TCP:3306✗ No
MongoDBBSON over TCP:27017✗ No
ClickHouseHTTP:8123 or TCP:9000⚠ HTTP only, with CORS
SQLite (embedded)In-process (no network)✓ Via WASM

What about WebAssembly?

WebAssembly (WASM) lets you run near-native code in the browser. Projects like PGlite compile PostgreSQL to WASM and run it entirely in the browser. This is remarkable engineering.

But it's an embedded database — it runs inside the browser tab, stores data in OPFS (the browser filesystem), and has no network connectivity. You can't use it to connect to your existing PostgreSQL server. It's great for development sandboxes and local prototyping, not for production database tooling.

The websocket workaround

Some tools proxy database connections through WebSockets. The architecture looks like:

Browser ←→ WebSocket ←→ Proxy server ←→ Database

This works, but the proxy server still has to exist somewhere. And now your credentials are flowing through a WebSocket connection to that proxy. You're back to the trust problem — whose server is the proxy on?

Our approach: local binary as PWA backend

Bun SQL Editor is technically a PWA — it has a manifest, a service worker, and can be installed to your desktop. But its "backend" is a local binary, not a cloud server.

The architecture:

PWA (browser) ←→ localhost:3000 (binary) ←→ Database

The PWA shell — all the HTML, CSS, JS — is served by the local binary and cached by the service worker. Once loaded, the UI works offline. Only the actual database queries require a live connection to the local binary.

This gives you the best of both worlds:

  • Install to desktop, native app feel (PWA)
  • Credentials never leave your machine (local binary)
  • No code signing headache (open source binary)
  • Works with any TCP-accessible database (direct connection)

The one friction point

The binary has to be running for queries to work. If you close the terminal, the app loses its backend. This is a real UX difference from a pure web app.

The solution is to set the binary to start automatically with your OS — add it to Login Items (macOS), Task Scheduler (Windows), or a systemd service (Linux). Then it behaves like any other background service: always running, accessible from the browser whenever you need it.

Is this the right trade-off?

For a personal database tool used by developers who already run local servers (Docker, local Postgres, Redis...), yes. Running one more background process is not a meaningful burden.

For a tool that needs to work on any device without any setup — a pure SaaS — the answer is no. But then you're back to trusting someone else's server with your database credentials. That's the fundamental choice: convenience vs. control.

We chose control.
