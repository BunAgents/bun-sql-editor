Why local? The case for a binary-first SQL editor

When we started building Bun SQL Editor, the obvious path was a cloud-hosted web app: deploy a backend, serve a frontend, done. Users would go to a URL, log in, and connect to their databases. Simple.

We didn't do that. Here's why.

The browser TCP wall

Browsers are intentionally sandboxed. They can make HTTP requests, open WebSockets, and use WebRTC — but they cannot open arbitrary TCP connections. This is a deliberate security boundary.

The problem is that every major database protocol lives on TCP:

  • PostgreSQL — wire protocol over TCP port 5432
  • MySQL — binary protocol over TCP port 3306
  • MongoDB — BSON over TCP port 27017
  • ClickHouse — HTTP (port 8123) or native TCP (port 9000)

ClickHouse is a partial exception because it has an HTTP interface — but even then, CORS and network topology make direct browser-to-database connections impractical in production.

The conclusion is unavoidable: any web-based SQL editor needs a backend proxy. There is no workaround. WebAssembly can run database engines inside the browser (PGlite does this for PostgreSQL), but those are embedded databases — they cannot connect to your existing external database server.

The trust problem

So every web SQL editor needs a proxy. The question is: whose server is it?

For cloud-hosted tools like Retool, Metabase Cloud, or browser-based SQL editors, the answer is: theirs. Your credentials — host, port, username, password — travel through their infrastructure to reach your database.

Even if they promise not to log credentials, you have no way to verify that. You're trusting:

  • Their security practices
  • Their employees with database access
  • Their infrastructure not being breached
  • Their terms of service not changing

For a database tool — something with read/write access to your production data — that's a significant trust surface.

What we did instead

The proxy has to exist. We just made you the proxy.

Bun SQL Editor is a small HTTP server that runs on your machine. Your browser connects to localhost:3000. The server connects to your database. Credentials go to localhost — never to any external server.

Browser → localhost:3000 (your machine) → Database

The server is stateless: it doesn't store credentials, doesn't log queries, doesn't have a database of its own. Every request from the browser includes the connection details, the server uses them to make the database connection, gets the result, and returns it. Then it forgets everything.

Why not a desktop app?

TablePlus, DBeaver, DataGrip — these are desktop apps precisely because they need TCP access. They solve the problem the same way: run something locally.

The downside of desktop apps is distribution. Code signing certificates cost $300–500/year per platform. Without signing, users get scary security warnings. With signing, you're paying for the privilege of users trusting a closed binary.

We distribute as a binary too — but an open-source one. The source code is public. You can read every line, build it yourself, and verify that what runs on your machine matches what's in the repo. The security warning on first run is a one-time friction, not an ongoing trust question.

The trade-off is real

The local binary approach has downsides:

  • Users have to download and run something
  • No access from a device that doesn't have the binary
  • No team collaboration features out of the box

For a personal database tool, we think these are the right trade-offs. Your data stays on your machine. You don't need an account. There's nothing to subscribe to.

If you need team access, run the binary on a shared machine inside your VPN and put an authentication proxy in front of it. You control the security boundary.

Open source as the trust anchor

The final piece is transparency. A closed binary — even a local one — still requires trust. We make the source code public so you don't have to take our word for it. Read app/server.ts. It's a straightforward HTTP server that routes requests to database adapters. There's no telemetry, no analytics, no call home.

That's the whole design: a proxy you control, with code you can read, running on a machine you own.
